# kb-eval — RAG 分块 / 召回 / 可答性 评测工具

回答三个具体问题，而不是靠感觉调参：

1. **改分块参数或分块策略，检索到底变好还是变坏？**（recall@K、mrr@10）
2. **送给模型的上下文，够不够回答问题？**（answered@K）
3. **任何一项改动，代价是多少？**（ctxChars@5 / xCost）

## 怎么跑

```bash
cd /e/reg-project/kb-eval && bash run_eval.sh
```

不带参数跑内置四组对照；也可以自己指定：

```bash
bash run_eval.sh "E-cn512:sentence_cn:512:0:" "S-cn256:sentence_cn:256:0:"
# 格式：name:strategy:size:overlap:separator
```

环境变量：

| 变量 | 作用 |
|---|---|
| `WINDOWS="0,1,2"` | 额外跑邻近扩窗对照；`0` 复现历史（不扩窗）数字 |
| `NEED_DIAG=1` | 对多事实问题打印**逐块** need 覆盖，用来判断 answered@K 有没有分辨力 |
| `RANKDIAG=1` | 打印**排序审计**：答案名次分布、各池大小的天花板、上下文成本、`min_score` 实际滤掉几条。零 API 成本（只用缓存向量） |
| `MINSCORE=0.75` | 配合 `RANKDIAG`，改掉默认的 0.6 阈值做假设检验 |

前置条件（脚本会自己处理大部分）：

- 开发库在跑（`docker` 容器 `adi-dev-postgres`），volcengine 的 key 从 `adi_model_platform` 表里读；
- 生产类已编译：`server/adi-common/target/classes` 必须是最新的（脚本直接用生产 `DocumentSplitterFactory`）。

## 组成

| 文件 | 作用 |
|---|---|
| `golden.jsonl` | 73 条题库：`{id, doc, query, gold, [need]}`。`gold` 是原文里逐字照抄的答案片段；`need` 见下 |
| `KbEval.java` | 主评测器：分块 → 嵌入 → 精确余弦检索 → 算指标。`SELFTEST=1` 只跑指标函数自检（不调嵌入） |
| `CtxDump.py` | 把每条题目的原文上下文（金标所在 markdown 块 ± 邻居块）导出成 `golden_review.txt`，供人工编写 `need` |
| `AddNeed.py` | 编写 / 校验 `need` 字段，并写回 `golden.jsonl`（`--write`）。任何片段在语料里找不到就报错退出 |
| `ChunkStats.java` | 只算分块统计（不调嵌入），用于跨语料/跨语言的快速体检 |
| `Diag3.java` | 验证 overlap 到底有没有生效（对比相邻块共享边界） |
| `Diag4.java` | 统计"单句超过配置尺寸"的比例，即兜底硬切会触发多少次 |
| `EmbProbe.java` | 嵌入通道冒烟测试（换 key / 换模型时先跑它） |
| `results-*.jsonl` | 每次运行的逐题明细（含 `need_missing@5` / `need_src@5`），可逐条核对 |

## 指标

### 分块质量（与嵌入模型无关）

- **intact**：金标片段能否被**某一个块完整容纳**。不 intact 意味着模型永远看不到完整答案。
- **overLimit**：估算 token 超过配置尺寸的块数（切分器没守住上限的硬指标）。

### 召回（文档级）

- **recall@K**：top-K 里有块覆盖了金标 ≥80%；**recall@K(strict)** 要求 100% 覆盖。
- **mrr@10**：第一个覆盖 ≥80% 的块的倒数排名。

### 可答性（语料级）

- **answered@K**：送给模型的上下文里，问题**真正需要的每一条事实**都在。
- **needCov@K**：这些事实的覆盖比例（部分得分，用于区分"差一点"和"完全没沾上"）。

`recall@K` 只问"装着答案的那个块有没有回来"。当一个问题需要两条分别落在两个块里的事实时——例如「重新切分子块会有什么后果」，答案同时需要表格里那行和它下面的 WARNING——单个片段可以被覆盖，而答案依然不完整。所以题库每条可以带 `need`：

```json
{"id":"g01", "doc":"…/segment.md", "query":"重新切分子块会有什么后果？",
 "gold":"会覆盖手动添加或编辑过的子块",
 "need":[["会覆盖手动添加或编辑过的子块"], ["删除该父段下全部子块及其向量"]]}
```

`need` 是**组的列表**，每组是一组**可选片段**（命中任一即可），所有组都满足才算 answered。没写 `need` 的条目退化为 `[[gold]]`，于是 answered@K 对单事实问题等价于片段覆盖。每个可选片段在装载时都会在对应文档里校验，写错会直接报错终止——宁可失败，也不要悄悄给出一个永远答不上的问题。

### ⚠️ 两个指标口径不同，不能相减

- `recall@K` 是**文档级**：答案片段所在的那个块，在不在 top-K 里。
- `answered@K` 是**语料级**：事实在不在模型收到的文本里（不管它来自哪篇文档）——这才是"能不能答"的真实判据。

本语料里 10 条金标片段在**别的文档里也逐字出现**（文档之间互相引用整段表格：同一段「严格/宽松」提示原文存在于 3 个文件）。所以 answered@K 合法地可能**高于** recall@K，那不是 bug。逐题的 `need_src@5` 会标出每条事实来自哪里：`S` = 问题自己的文档，`O` = 另一篇文档，`-` = 缺失。

## 设计上必须知道的三件事

1. **偏移量按"去掉空白"的文本对齐。** langchain4j 的段落/行/句切分器重建块时会丢掉原始换行，块不是原文的逐字子串；但它一定是"去掉空白后"的子串。覆盖率由此做区间求交，精确且不猜。
2. **题库自校验。** 每条 `gold` 必须在指定文档里**唯一可定位**，`need` 的每个片段必须能找到；出错就直接抛异常终止，绝不放行。改文档后如果没同步题库，脚本会立刻失败而不是悄悄给出错误分数。
3. **嵌入结果按内容哈希缓存**（`results-emb-cache.tsv`）。重复跑、加对照组的成本接近零——这也是能放心扩题库的原因。

## 边界（不要过度解读）

- 检索只用**精确余弦**，没有混合检索、没有 rerank、没有 `min_score` 阈值——这里量的是分块与排序，不是 rerank 模型。
- 语料是产品文档（37 篇中文 markdown），**不是**客户真实知识库；结论方向可迁移，绝对值不可直接搬。
- n=73，1 条 = 1.4 个百分点。差异在 1–2 条量级时只算提示，不算结论。
- 嵌入模型是 volcengine `doubao-embedding-vision`(2048)。换成 BGE-512（上限 512 token）时，1000 token 的块会被截断，结论可能不同。
- **可答性只测"事实在不在"，不测"表达得好不好"**。它不能替代 LLM 裁判；`need` 是人写的，写漏了指标就发现不了。

## 查询侧改写：实测**否决**（2026-09-22）

检索链路里没有任何查询侧处理（用户问题逐字向量化）。对两类经典做法做了真实 A/B，`q=` 参数可选：

```bash
WINDOWS="0,1" QWMODES="off,mq,mq-rrf,hyde-rrf" bash run_eval.sh "Q-cn512:sentence_cn:512:0"
```

`mq` = LLM 生成 3 条改写查询，逐条检索、每块取最高分（max-cosine）；`hyde` = LLM 写一段假设性答案正文，直接用它的向量检索；`*-rrf` = 同样有多个查询，但用 **RRF 融合名次**而不是取最高分。改写结果按 `(提示词族, 提示词版本, N, 模型, query)` 缓存，重跑零成本。

### 结果（sentence_cn/512）

| 模式 | recall@5 | ans@5 | mrr@10 | ctxChars@5 | LLM 调用/问 |
|---|---|---|---|---|---|
| off（基线，w0） | 95.9% | 95.9% | 0.724 | 2658 | 0 |
| mq v1（"语义相同、措辞不同"） | 95.9% | 95.9% | 0.719 | 2560 | 1 |
| mq v2（要求换角度/换术语） | 93.2% | 93.2% | 0.714 | 2676 | 1 |
| mq-rrf | 94.5% | 94.5% | **0.740** | 2712 | 1 |
| hyde（max-cosine） | 90.4% | 91.8% | 0.678 | 2724 | 1 |
| hyde+q | 90.4% | 91.8% | 0.683 | 2725 | 1 |
| **hyde-rrf** | **97.3%** | **97.3%** | 0.716 | 2706 | 1 |
| w1（已建成的扩窗，零 LLM） | 97.3% | 97.3% | **0.798** | 5233 | 0 |
| **w1 + hyde-rrf** | **98.6%** | **98.6%** | **0.801** | 5220 | 1 |

### 三个可迁移的发现

1. **融合方式比改写本身更重要。** 同一批 HyDE 改写：max-cosine 下 recall@5 只有 90.4%（比基线低 5.5pt），换成 RRF 融合变成 97.3%（高 1.4pt）——**7 个百分点只来自换融合公式**。mq 同理：93.2% → 94.5%，MRR 0.714 → 0.740。与项目里混合检索的选型一致：**多来源打分该用名次融合，不该取最高分**（max 让单个"过于自信"的改写直接压过正确答案）。
2. **两个机制单独用都是有害的，且原因可查。**
   - HyDE 的段落是**流畅但编造的产品行为**（对"云端/锁形图标代表什么"答出"端到端加密存储""账号二次验证"——产品里没有）；它把检索拉向主题相邻的错误文档（`capability-tts.md` → `voice.md`）。作为**分数来源**有害，作为**名次投票者**才有用。
   - MQ 第一版提示词（"语义相同、措辞不同"）产出近乎同义句（"需要做什么操作/要做哪些事情/需要完成哪些工作"），向量几乎重合。改成要求"换切入角度、换术语"后多样性明显提高（"触发原理/实现逻辑"），结果反而**更差**（93.2%）——更抽象的说法命中了错的文档。
   - **两者的共同副作用是"降级"**：把本来排第 1 的正确答案推下去（hyde 把 g27 从 1 推到 6；mq 把 g27/g54/g72 从 1 推到 2–4）。用户措辞本来就好时，任何额外查询都只增加"抢票"的对手。
3. **相对已建成的扩窗，增量落在噪声里。** 组合（w1 + hyde-rrf）拿到 98.6% / MRR 0.801，比只用扩窗（97.3% / 0.798）**多 1 题**——n=73 下 1 题就是 1.4pt，**无法与噪声区分**。代价是每次提问多 1 次 LLM 调用 + 1–3 次嵌入调用，以及**可复现性**：整条检索的名次开始依赖某个 LLM 在某个温度下的改写（本项目已实测 `invokeLLM` 裸调用三次运行有 1.7% 摇摆，且 temperature=0 也不能保证复现）。知识库产品要求同一问题答案稳定，这是可靠性退步。

### 结论

**不落地到应用代码（零迁移、零前端改动）。** 上下文侧（分块 + 扩窗，纯 SQL/零 LLM）已经把可拿的收益拿完；查询侧改写在 n=73 上拿不出可分辨的增量，却要在每个提问的关键路径上引入一次 LLM 调用与不可复现性。

需要复看时的边界：只用了一个改写模型（`doubao-seed-2.0-lite`）、一版提示词、一个 RRF 常数（60）；题库是从文档写出来的、措辞本就贴近文档，可能低估改写对真实口语提问的价值。**若将来重开这个方向，先做两件事：把题库扩到"真实用户问法"，以及评估 hyde-rrf 的 run-to-run 稳定性。**

## 排序审计：池大小才是天花板（`RANKDIAG=1`，2026-09-22）

上两节的 recall@5 都在**手工截 top-5** 的前提下算的。生产不是这样：它按 `retrieve_max_results`
取一批候选就交给模型。`RANKDIAG=1` 补上的正是这条信息——**答案在纯余弦序里排第几**，以及由此推出的
「池子要多大」。跑法（纯内存余弦，复用嵌入缓存，零 API 成本）：

```bash
RANKDIAG=1 bash run_eval.sh "Q-cn512:sentence_cn:512:0:"   # 或直接给 java 加 RANKDIAG=1
```

### 实测（sentence_cn/512，w=0）

```
答案名次分布：  r1=41  r2=15  r3=7  r4-5=7  r6-10=3      ← 只有 56% 的问题答案排第 1
recall@K：       @1=56.2%  @2=76.7%  @3=86.3%  @5=95.9%  @10=100.0%
```

| 池大小 | 答案在池内（=任何完美重排能达到的 recall@5 上限） | 平均上下文 | xCost |
|---|---|---|---|
| 3（表默认值，改动前） | **86.3%** | 1651 字符 | 0.62 |
| 5（改动前的自适应上限） | 95.9% | 2658 字符 | 1.00 |
| **10（本次上限）** | **100.0%** | 5376 字符 | 2.02 |

### 三个结论

1. **重排救不了池外的东西。** 池=3 时 13.7% 的问题答案根本不在候选里——这不是排序问题，是取数问题。
   任何 rerank / 改写 / 扩窗组合的上限都是 recall@pool，与模型多好无关。
2. **这一项的上限是「配置」，不是「功能」：池 5→10 把 95.9% 提到 100%，零模型调用、零新依赖。**
   应用侧对应 `AdiConstant.RAG_RETRIEVE_NUMBER_MAX`（5→10）与迁移 027（表默认值 3→0=自动）。
3. **它同时说明了扩窗与扩池的分工**：w1（扩窗）在池=3 上拿到 97.3% / MRR 0.798、上下文 5233 字符；
   池=10 在**几乎同样的上下文成本**（5376 字符）上拿到 100%。两者在"答案是否进入上下文"这个指标上
   可以互相替代；扩窗额外修的是"答案是否**完整可读**"（条款与其例外、表头与表体），那是 recall 测不到的，
   所以两者不是替代关系，只是**别把扩窗当成召回手段**。

### ⚠️ `min_score` 的量纲陷阱（差点据此写出一条假结论）

pgvector 存里 `score` **不是余弦**，是把余弦距离压到 [0,1]：

```sql
SELECT (2 - (embedding <=> ?)) / 2 AS score ...   WHERE (embedding <=> ?) <= 2 - 2 * minScore
```

即 `score = (1 + cos) / 2`，所以默认 `retrieve_min_score = 0.6` 等价于 **cos ≥ 0.2**。
拿原始余弦去比 0.6 会得到"几乎所有块都被阈值滤掉"的结论——本次实测金标块的 store score
min=0.631 / median=0.728，**0 条被滤掉**，阈值是个近乎空转的保护。`storeScore()` 里带了注释与
`SELFTEST` 断言，改这块代码前先读它。

## 语料跨文档重复排查 + 评测 doc-lock 修正（2026-09-23）

上一轮把"下一步"指向语料本身，假设"10 条金标片段跨文档逐字重复、同一张表在多个 guide 各存一份"。
`CorpusDup.py`（只读）把 `docs/cn` 全量扫了一遍，结论是否定这个假设的：

| 维度 | 实测 |
|---|---|
| 金标片段跨文档 | **8/73** 题有 ≥1 片段出现在 2–3 份文档（如"严格模式"在 `kb-qa/manage/workflow`，"始终需要"在 `capability-asr/image/tts`）——**合法互引**，不是复制 |
| 块级重复 | **仅 1 块**（261 字"前置步骤：注册平台名称常量"被复制到 3 份 dev 能力指南） |
| 表格级重复 | **0 张** |

→ **不值得做批量语料改写**：重复是轻量且多半合理的互引，动产品文档收益低、风险高（唯一可顺手做的是把那 261 字抽成一处引用，低优先）。

**顺带发现并修掉一个评测度量假阴（本轮真正的产出）。** 评测器 `coverage()/unionCoverage()/goldScore()` 用
`c.doc.equals(g.doc)` 把金标**钉死在单一归因文档**。语料在多个 guide 里重复同一事实，当检索把"相同文本"从
**兄弟文档**返回时，评测误记成 miss。修正：Gold 加载时扫全语料收集所有"含该片段（及每个 need 备选）"的文档进
`goldDocs`，三处判定改用 `sameGoldDoc(g,c)=goldDocs.contains(c.doc)`（self-test 中 `goldDocs=null` 回退旧行为，兼容合成数据）。

效果（sentence_cn/512，向量已缓存、零 API）：

```
w=0：recall@5  70/73 → 71/73  (95.9% → 97.3%)   回收 1 条被假阴吞掉的问题
w=1：recall@5  71/73 不变（邻窗本就把它覆盖）
residual K=5 失败：3 → 2 条，仍是 g10/g73/g53 一类真排序缺口（在 top-10 但排不进 top-5）
```

度量口径因此更正确：**RAG 评测里"从任一含答案的文档取回"都算命中**，钉死单文档会系统性低估跨文档语料的召回。

> ⚠️ **`check_init` 的红要分清结构层 vs 数据层**：结构层（DDL）`TOTAL DIFF LINES=0` = 迁移改动已进 `all_ddl.sql`（027/028 已确认同步）；
> 数据层 4 行 diff（`mock-e2e-7b-ft` 模型、`default_locale` 配置、`ApiSweep*` 工作流组件、`apitest@/intruder@` 用户）是 dev 库**运行时/测试数据**，
> 非本人引入，也不该进初始化种子（临时测试数据进 `all_dml` 会污染全新安装）。

## 结论：瓶颈是排序，不是上下文组装

1. **可答性不是瓶颈。** 在测过的全部 8 个配置下，`answered@K` 与 `recall@K` 的差距都在 1 条（1.4pt）以内，且两处差异都能逐条解释（跨文档冗余、片段被切散）。6 个多事实问题里，top-1 命中块**总是**同时包含全部必需事实——`NEED_DIAG=1` 可以看到（例如 g37 在 rank 4/6 的块只覆盖 0.5，证明指标能分辨，只是这里用不上）。
2. **残余失败是纯排序失败，而修它的不是排序模型，是池子大小。** 512 配置下 3 条未进 top-5：g10、g73 的答案块排第 **8**、g53 排第 **6**。上下文侧的手段（扩窗、citation、overlap）确实都修不了它——但**把池子从 3/5 提到 10 就直接修好了**，因为它们的答案一直就在 top-10 里（recall@10 = 100%），只是没被取出来。这一条是本节最值得记住的：**在找"更好的排序"之前，先问"候选有没有被取回来"。**
3. **查询侧改写修不了它**（见上一节）：g10/g73 在测过的每种改写方案里都没能稳定进 top-5，因为问题不在措辞，在候选池。
4. 于是**当前投入产出最高的是**：默认 `sentence_cn/512` + 召回上限 10（迁移 027 已落地）+ 对需要跨段答案的知识库打开 `retrieve_neighbor_enabled`（半径 1）。**不建议引入 rerank**：它买不到召回（池=10 已经是 100% 上限），只买到"用更少的上下文保住同样的召回"；而且本项目目前唯一配了 key 的平台（火山方舟）没有 Cohere 形状的 rerank 端点，开启前得先补一个兼容平台的凭证（详见 `OpenAiCompatibleScoringModel` 的类注释）。
5. **语料本身经排查不是问题**：跨文档重复实测是 8/73 轻量互引 + 1 块 261 字 + 0 重复表（详见上节），不值得批量改写。真正顺带修掉的是评测器的 doc-lock 度量假阴（回收 1 条假阴）。
