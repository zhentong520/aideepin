# 二、关键缺口（5 项，按 ROI 排序）

## 🔴 GAP-1 检索层无 ACL：权限只做到"库级"，没做到"片段级"

实测 `CharacterChatHelper.retrieve()`：

```
filter = new IsIn(KB_UUID, kbUuids)   // 只有库 UUID
```

- `KnowledgeBase` 实体有 `ownerUuid` / `isPublic` 字段，但**只用于"我能看到哪些库"的列表过滤，从未进入向量检索的 where 条件**
- 后果：任何人只要被关联了 KB A，就拿到了 A 的**全部片段**，无密级、无部门、无行列级
- 业界共识（多个来源一致）：权限过滤**必须发生在向量检索阶段**，塞进 prompt 是无效的；"先取 top50 再筛"会吃掉有效召回

**改造建议**：chunk 入库时固化 `tenant_id / visibility_group / sensitivity`（迁移 035 + 回填脚本），检索侧 `IsIn` 叠加为 `And(IsIn(KB_UUID,...), IsIn(VISIBILITY_GROUP, userGroups))`，并在取回后加一次应用层断言双保险。
**成本**：P0，2–3 天（回填脚本需单独跑）

## 🔴 GAP-2 知识库"出不去"：不能被外部 Agent / 业务系统当知识层用

这是"即插即用"的**正面缺口**。当前 `/ext/v1/knowledge` 只提供 `POST` 一个端点：**给定一个 key 绑定的单个 KB，做问答（blocking/SSE）**。

- 不能"只检索不生成"（外部系统往往要自己拼 prompt）
- 不能一次查多个库
- **没有 MCP Server 形态** —— 微信 WeKnora（23.4k star）正是靠 `API + CLI + MCP Server` 三件套，让 Claude Code / Cursor / DeepSeek Harness 共享同一企业知识层
- 不能被工作流以外的业务系统（OA/CRM/ERP）挂载

**改造建议（这是最高价值的一步）**：
1. `POST /ext/v1/knowledge/retrieve` —— 纯检索，返回片段 + 出处 + score（不带 LLM），支持 `kbUuids[]` 多库
2. **知识库导出为 MCP Server**（`/mcp` 模块已有基础设施，新增 resource 类型 `knowledge`），让任意 MCP 客户端挂载
3. 与 `/skill` 打通：**一个"知识包"= Skill 描述 + KB 绑定 + 提示词 + 检索配置**，可导出 ZIP（admin 端 Skill 导出 ZIP 的能力已有，复用）

## 🟡 GAP-3 没有运行时可观测：无法回答"这次答得对不对"

现有 `tokenMonitor` 只管 token 消耗，**没有 RAG 质量指标**。业界基线要求：

| 缺失 | 后果 |
|---|---|
| 引用可追溯率（抽 100 条答案有几条能点回原文） | 答对了但说不清来源，无法追责 |
| 低置信/拒答记录 | 失败案例无从收集 |
| 检索日志（主体、过滤表达式、召回片段 id） | 过滤失效无法定位 |
| 每次问答的成本与延迟 p95 | 无法做容量与降级决策 |

**改造建议**：迁移 035 建 `adi_rag_query_log`（query / 主体 / kbUuids / 召回片段 id+score / 是否命中扩窗 / rerank 耗时 / LLM 耗时 / token / 用户反馈 thumbs），管理端加"检索质量"看板。
**注意**：项目已有 `E:/reg-project/kb-eval` 离线评测器（recall@K / answered@K / MRR），**把它的口径搬上线做趋势看板**，是零算法成本的高价值动作。

## 🟡 GAP-4 记忆只有"角色维度"，没有"用户/业务维度"

现状记忆绑定 `characterId`，只能记住"这个角色记得什么"。阿里云 Memory Studio 拆三类：**观察记忆（发生过什么）/ 用户记忆（你是谁）/ 技能记忆（这事过去怎么做的）**。

- 我们已有 semantic + episodic 双通道，**结构上不缺**，缺的是：记忆的用户确认环节（自动提取后等用户确认再写入）、可视化管理入口、跨 Agent 共享
- **业务侧价值**：把"某客户上月报过的口径""某流程上次怎么处理的"沉淀下来，新人/新 Agent 直接可用 —— 这才是"知识库用到各个业务上"的第二条腿

## 🟡 GAP-5 能力都是"平台内闭环"，缺开放面

| 已有 | 缺 |
|---|---|
| 工作流 20 节点（含 MCP/Skill/Database） | 工作流**版本化 + 发布 + 灰度**（现在改了直接生效） |
| 场景（scene）管理 | 场景一键导出/分享给别人用 |
| Skill 脚本 | Skill **市场/模板库**（阿里云的做法：广场严选 / 服务商直供 / 用户自定义三层） |
| 文档来源 URL/API（031） | 数据源连接器生态（飞书 / Notion / Confluence / GitLab —— WeKnora 已内置） |

# 四、"知识库即插即用"的目标形态

```
                  ┌─────────────────────────────────────┐
   新业务系统 A ──┤  ① HTTP: POST /ext/v1/knowledge/      │
   （OA/CRM/ERP）│     retrieve  只检索不生成              │
                  │  ② MCP : kb-{uuid} 作为 resource 挂载  │
   Cursor/ClaudeCode┤  ③ Skill: 知识包(SKILL.md + KB绑定)  │
   ──────────────┤  ④ 工作流: KNOWLEDGE_RETRIEVER 节点    │
   本系统各页面 ──┤  ⑤ 记忆: 用户维度沉淀跨会话经验         │
                  └─────────────────────────────────────┘
                              同一个检索内核
                        （混合检索+RRF+rerank+扩窗）
```

**判定"即插即用"成功的标准**：新建一个业务系统接入本知识库，**≤1 天、0 代码改动核心链路**（只需申请 API Key 或填 MCP 地址）。

# 五、建议执行顺序

| 阶段 | 内容 | 周期 | 理由 |
|---|---|---|---|
| **P0-1** | 检索层 ACL（035 迁移 + 回填 + 双保险断言） | 2–3 天 | 安全底线，不可后置 |
| **P0-2** | `/ext/v1/knowledge/retrieve` 纯检索端点（支持多库） | 1–2 天 | 成本最低、复用面最广 |
| **P0-3** | KB → MCP Server（复用 `/mcp` 基础设施） | 3–5 天 | 差异化最大，对标 WeKnora 核心卖点 |
| **P1-1** | `adi_rag_query_log` + 引用可追溯率 + 质量看板 | 3 天 | 让效果可证明、可汇报 |
| **P1-2** | 知识包（Skill + KB 绑定）可导出可分享 | 3 天 | "即插即用"的载体 |
| **P1-3** | 记忆加用户维度 + 写入前确认 + 管理入口 | 5 天 | 跨会话价值 |
| **P2** | Wiki 模式、连接器生态、工作流版本化 | — | 视客群再定 |

# 六、需要你拍板的 3 件事

1. **对外开放的安全边界**：知识库一旦可被外部系统挂载，"库级权限"立刻不够用 —— P0-1 是否现在就做？（建议做，且**先于** P0-3）
2. **目标客群**：主要服务内部（工作流+Agent），还是要把知识能力卖给外部业务系统/其他团队？这决定 P0-3 MCP 与 P2 生态的优先级。
3. **数据源扩展方向**：客户最想要哪几个（飞书 / Notion / Confluence / 企业微信文档 / 数据库直连）？按 034 已有分类机制扩展即可。
