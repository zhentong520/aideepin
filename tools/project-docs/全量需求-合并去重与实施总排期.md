## 一、合并前必须先解决的三件事

### 1.1 排序冲突：门禁 vs 日志，谁先做

| 文档 |主张 |

**三者其实不冲突，是三道不同的门禁**，之前被混在一起讨论了。合并后明确为三层，各管各的：

| 门禁 | 管什么 | 何时建 | 出处 |
|---|---|---|---|
| **G-CI 工程门禁** | 代码能不能合（类型检查、单测、i18n 花括号、补丁有效性） | 第 1 周，最先 | ③F1 / ②P2-33 |
| **G-EVAL 行为门禁** | 改了检索/生成行为后效果有没有变差 | 与 A-02 同批，**不晚于第 2 周** | ①EVAL-01/02/03 |
| **G-ACL 安全门禁** | 越权泄露率是否为 0 | A-02 先建，A-03~A-06 每步跑 | ④A-02 |

> 顺序结论：**G-CI（第1周）→ G-ACL 的评测集（第2周，与线A同批）→ G-EVAL（随 EVAL 任务落地）**。

### 1.2 「六处注册」铁律 vs 「WfNodeFactory 不存在」的误判

**文档③ 1.3 节结论错误，需以实测为准。**

| 项 | 文档③ 的说法 | 实测结论 |
|---|---|---|
| `WfNodeFactory` | 「不存在节点工厂/注册表机制」 | ❌ **错误**。文件存在：`aideepin/server/adi-common/src/main/java/com/moyz/adi/common/workflow/WfNodeFactory.java`，含 **20 个 `case` 分支**（START / LLM_ANSWER / CLASSIFIER / SWITCHER / TEMPLATE / KEYWORD_EXTRACTOR / DOCUMENT_EXTRACTOR / FAQ_EXTRACTOR / KNOWLEDGE_RETRIEVER / GOOGLE_SEARCH / OPENAI_IMAGE / TONGYI_WANX / HUMAN_FEEDBACK / MAIL_SEND / HTTP_REQUEST / AGENT / DATABASE / MCP / SKILL / END），并有配套单测 `WfNodeFactoryRegistrationTest` |

**但文档③ 的核心诉求成立**——它说的是**前端**没有描述化注册机制，两件事不冲突：

| 层 | 现状 | 加一种节点的代价 |
|---|---|---|
| 后端执行层 | ✅ 有工厂（`WfNodeFactory`，20 分支） | 加 1 个 case |
| 前端描述层 | ❌ 无。**六处硬编码**：`nodes/index.ts` → `WorkflowDefine.vue` slot → `WfDefineRightPanel.vue` → `workflow-util.ts` → locales 中英文案+`componentTitle` → `RuntimeNodes.vue` 指标 chip | 加 6 处，漏第 6 处 = 指标入库不显示 |

→ 因此 **W-04「节点描述化」保留 P0**，但任务描述要改：不是「造工厂」（后端已有），而是**把前端六处收敛成一份描述文件**。这是 ③D4 的真实价值点。
