## 一、背景与目标

### 1.1 背景

系统当前的知识能力存在一个结构性偏斜：

- **「怎么检索」已经做到了 90 分**。混合检索（向量 + BM25，迁移 017）、RRF 融合、Rerank（迁移 030 千问 maas 实跑通）、命中片段左右扩窗（026）、候选池上限 10（027）、中文分句 `sentence_cn`/512/overlap=0（025）、出处抬头 `【文档名·第N段】`（024）——链路指标已对齐一线实践，离线评测（`E:/reg-project/kb-eval`，73 条金标）显示 recall@10 达 100%。
- **「谁能用、怎么被复用、怎么被观测」几乎空白**。这是本 PRD 要解决的问题。

### 1.2 三个已核实的问题

**问题一：检索层没有 ACL（安全底线失守）**

实测 `adi-common/.../util/CharacterChatHelper.retrieve()` 第 131 行：

```java
.filter(new IsIn(KB_UUID, kbUuids))
```

向量检索的 where 条件**只有 `kb_uuid`**。`adi_knowledge_base` 表上的 `owner_uuid` / `is_public` / `owner_id` 字段**仅用于「我能看到哪些知识库」的列表过滤**（`KnowledgeBaseService.searchMine`），从未进入检索过滤条件。

后果：任一用户 / Agent / 工作流只要被关联了知识库 X，就获得了 X 的**全部片段**，无密级、无部门、无行列级边界。系统已有公开库 + 私有库的混合形态，且已具备对外 API（`/ext/v1/knowledge`），一旦对外开放，**库级权限远远不够**。

行业共识（多个独立来源一致）：权限过滤**必须发生在向量检索阶段**；塞进 prompt「请只回答用户有权查看的内容」是无效的，因为模型不在访问控制链路上；「先取 top-50 再按租户筛」看似省事，实际会吃掉大量有效召回，且多出一个「过滤后为空」的分支。

**问题二：知识库「出不去」——即插即用的正面缺口**

`adi-chat/.../externalapi/v1/ExtKnowledgeBaseController.java` 全文只有一个端点：

```
POST /ext/v1/knowledge
```

- Key 与**单个**知识库一一绑定（`ThreadContext.getExtApiEntityUuid()` 即 kbUuid）
- 只能**问答**（blocking / SSE 两种响应模式），**不能「只检索不生成」**
- **不能一次查多个库**
- **没有 MCP Server 形态** —— 外部 AI 工具（Coding Agent、IDE）无法挂载

对标：腾讯微信开源的 WeKnora（GitHub 23.4k★）的核心卖点正是 `API + CLI + MCP Server` 三件套，让 Claude Code / Cursor / DeepSeek Harness 等不同 Harness 共享同一个企业知识层。我们的 `/mcp` 模块已有完整基础设施，**只差把 knowledge base 作为一种 resource 接进去**。

**问题三：运行时不可观测**

`admin-web` 的 `tokenMonitor` 模块只统计 token 消耗。系统**没有**：

- 引用可追溯率（抽 100 条答案，有多少条能点回原文）
- 检索日志（谁、何时、检索了哪个库、过滤表达式、召回了哪些片段）
- 低置信 / 拒答 / 用户负反馈的收集入口

后果：RAG 效果「变好了还是变差了」无法回答，也无法向业务方证明。而项目**已经有** `E:/reg-project/kb-eval` 离线评测器（recall@K / answered@K / MRR / needCov@K），把它的口径搬到线上做趋势看板，**是零算法成本的高价值动作**。

**附带问题**：长期记忆目前绑定 `characterId`（`CharacterMemoryEmbedding` 语义通道 + `EpisodicMemoryEmbedding` 情景通道），只能记住「这个角色记得什么」，无法承载「这个用户 / 这条业务线记得什么」，跨 Agent 更是无法共享。

### 1.3 成功指标

| 编号 | 指标 | 口径 | 当前 | 目标 |
|---|---|---|---|---|
| M-1 | 片段级越权召回率 | 越权测试集中，无权片段进入上下文的比例 | 未测（**推定 > 0**） | **0%** |
| M-2 | 外部系统接入成本 | 新业务系统从申请 Key 到跑通首个检索的工时 | 不适用 | **≤ 1 人日，0 代码改动核心链路** |
| M-3 | 引用可追溯率 | 抽 100 条答案，能点回原文的条数占比 | 无口径 | **≥ 95%** |
| M-4 | 可观测覆盖率 | 每次问答都有完整检索日志的比例 | 0% | **100%** |
| M-5 | 记忆命中率 | 已确认记忆被后续会话正确召回的比例 | 无口径 | 建立基线后 ≥ 80% |

## 二、名词与术语

| 术语 | 定义 |
|---|---|
| 可见组（Visibility Group） | 能看见某条片段的主体集合，如 `dept_rd`（研发部）、`role_admin`。系统内以字符串标识 |
| 密级（Sensitivity） | 片段的保密等级：`PUBLIC` / `INTERNAL` / `CONFIDENTIAL` / `SECRET` |
| 知识检索 API | `POST /ext/v1/knowledge/retrieve`，只做检索返回片段，不调用 LLM |
| 知识包（Knowledge Pack） | 一个可导出可分享的资产 = 知识库绑定 + 检索参数 + 提示词 + 可选 Skill 脚本，打包为 ZIP |
| KB MCP Server | 把一个知识库以 MCP 协议暴露出去的独立服务，供任意 MCP 客户端挂载 |
| 检索日志 | 一次检索/问答的完整可审计记录（主体、库、过滤条件、召回片段、耗时、token、反馈） |
| 长期记忆（用户维度） | 绑定 userId 而非 characterId 的记忆，供该用户的所有 Agent / 场景共享 |

## 四、方案对比与选型说明

### 4.1 M1 ACL 的三种方案

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 入库固化 + 检索 where 过滤 | chunk 向量写入时带 `visibility_groups` / `sensitivity`；检索时 `And(IsIn(kb_uuid), IsIn(visibility_groups, userGroups), Or(IsEq(sensitivity,PUBLIC), ...))` | 权限在检索层生效，行业标准做法；召回即合规 | 存量 chunk 需回填 | ✅ **采纳** |
| B. 权限塞进 prompt | 在 system message 里写「只回答用户有权查看的内容」 | 零改动 | **完全无效**——模型不在访问控制链路上 | ❌ 否决 |
| C. 取回后再筛 | 先取 top-N，再按主体过滤 | 实现简单 | 有效召回被吃掉大半，多一个空分支 | ❌ 否决 |

**选定 A**，并额外加一层「取回后应用层断言」作为防御纵深（双保险，两道都过才进上下文窗口）。

### 4.2 M3 KB → MCP 的三种方案

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 内置 MCP Server 端点 | 在 adi-chat 增加 `/mcp/kb/{uuid}` SSE/Streamable HTTP 端点，把 KB 注册为一个 MCP server | 复用现有 `/mcp` 基础设施与鉴权；部署简单 | 与主应用同进程，公网暴露面需管控 | ✅ **采纳** |
| B. 独立 sidecar 进程 | 每个 KB 一个独立检索服务 | 隔离彻底 | 运维成本 ×N，与单体架构现状不匹配 | ❌ 否决 |
| C. 离线导出知识包 | 导出 chunk + 向量到本地 MCP | 不依赖本系统 | 数据一致性无法保证，等于快照 | ❌ 否决（作为 M5 的补充形态保留） |

### 4.3 演进路径

**本期（M1–M6）** → 安全可控地对外开放知识能力 → **后续版本池**：Wiki 模式、数据源连接器生态、工作流版本化发布、Skill 三层市场。

## 五、用户角色与使用场景

### 5.1 角色

| 角色 | 描述 | 本期相关模块 |
|---|---|---|
| 知识库管理员 | 创建/配置知识库与文档，管理可见组与密级 | M1 / M4 / M5 |
| 业务用户 | 在问答页使用知识库 | M1（被过滤方）/ M4 |
| 外部系统开发者 | 用 API Key 或 MCP 接入本知识库 | M2 / M3 |
| 平台运维 | 监控检索质量、成本、异常 | M4 |
| Agent 开发者 | 在工作流/Agent 中使用知识检索 | M1 / M2 / M6 |

### 5.2 核心场景

**场景一（主场景）：外部业务系统接入**
OA 系统需要回答「差旅报销标准是什么」。OA 开发者申请一个 knowledge 类型的 API Key，拿到 `POST /ext/v1/knowledge/retrieve` 端点，在自己系统里拼 prompt 调用。检索到的片段全部带 ACL 过滤，只有 OA 所属部门可见的内容会返回。

- 主流程：申请 Key → 调 retrieve → 拿到片段 + 出处 → 自建 prompt → 展示答案（带出处可点回）
- 分支：某库无权限 → 该库被静默跳过并在响应 `skippedKbUuids` 中列出
- 异常：Key 失效 → 401；库已删除 → 404；检索超时 → 504

**场景二：IDE / Coding Agent 挂载**
开发者在 Cursor 中配置 `kb-{uuid}` 为 MCP server，问「项目的部署流程是什么」，Agent 主动调用 `kb_search` 工具，返回片段与出处。

**场景三：跨会话记忆**
用户 A 上周问过「报销上限是多少」，系统提取为记忆并经用户确认。用户 A 下周换一个 Agent 问「出差住宿标准」，系统召回该记忆并回答——即使换了 Agent 和会话。

## 六、功能需求

### 模块 M1：知识库片段级访问控制（ACL）· P0

#### M1.1 数据模型

**FR-M1-001** 系统应在文档分块入库时，为每个 chunk 固化以下访问控制元数据（写入向量库 metadata）：

| 字段 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `acl_visibility_groups` | varchar | 继承文档 | 可见组，逗号分隔；空表示「所有人可见」 |
| `acl_sensitivity` | varchar(16) | `INTERNAL` | 密级，取值 `PUBLIC`/`INTERNAL`/`CONFIDENTIAL`/`SECRET` |

**业务规则**
- BR-1：`acl_*` 属于 chunk 的**固化属性**，与分块策略（`sentence_cn`/512/overlap=0）解耦，**修改分块参数不得丢失 ACL 字段**。
- BR-2：ACL 字段**不参与向量化**，仅用于检索过滤与审计，因此修改 ACL **不需要重建向量索引**。
- BR-3：ACL 字段缺失（存量数据）时，**按库级 `owner_uuid + is_public` 推导**，并在管理端标记为「待规范化」，提示管理员执行回填。

**Given/When/Then 验收**
- Given 一篇文档属于部门「研发部」，管理员将其 ACL 设为 `dept_rd`
- When 该文档完成分块入库
- Then 每个 chunk 的 metadata 含 `acl_visibility_groups=dept_rd` 且 `acl_sensitivity=INTERNAL`
- And 管理员随后将 ACL 改为 `dept_ops`，**无需重建索引**，新检索立即生效

#### M1.2 存量回填

**FR-M1-002** 系统应提供存量 chunk 的 ACL 回填能力：
- 提供 SQL 脚本 + 后端一次性任务两种方式
- 回填规则：`acl_visibility_groups` = 该文档所属库的 owner_uuid（私有库）或空（公开库）；`acl_sensitivity` = `INTERNAL`
- 回填为**幂等操作**，可重复执行
- 回填过程**不得删除或重建向量**，仅 UPDATE metadata

**验收**
- Given 环境有存量知识库数据
- When 执行回填脚本两次
- Then 第二次执行影响行数为 0（幂等），且期间检索服务不中断

#### M1.3 检索侧过滤

**FR-M1-003** 所有知识库检索路径**必须**在向量检索的 where 条件中应用 ACL 过滤，包括但不限于：

| 检索入口 | 文件 |
|---|---|
| 对话检索 | `CharacterChatHelper.retrieve()` |
| 知识库问答页 | `KnowledgeBaseService.sseAsk` / `blockingAsk` |
| 工作流 KNOWLEDGE_RETRIEVER 节点 | 对应节点实现 |
| Agent 工具检索 | Agent 工具调用链 |
| 新增 M2 检索 API | M2 新增代码 |

**过滤表达式**

```java
And(
  IsIn(KB_UUID, authorizedKbUuids),
  Or(
    IsEqualTo(ACL_SENSITIVITY, "PUBLIC"),
    IsIn(ACL_VISIBILITY_GROUPS, currentUserGroups)
  )
)
```

**业务规则**
- BR-4：**过滤条件必须来自请求主体**（登录态、租户上下文、Key 绑定的可见组），**严禁来自用户输入或 query 内容**。
- BR-5：Agent / 工作流发起检索时，可见组取**发起者的用户上下文**，不得使用 Agent 自身的默认组。
- BR-6：系统应采用**双保险**——向量库侧 metadata 过滤一次，取回后应用层再断言一次，两道都通过才允许进入上下文窗口。断言失败的片段**直接丢弃并写审计**，**不得**「拿给模型参考一下」。

**Given/When/Then 验收**
- Given 用户 u 属于组 `dept_rd`，库 X 含片段 A（组 `dept_rd`）与片段 B（组 `dept_fin`）
- When u 在问答页提问，命中 A 与 B
- Then 上下文中**只有 A**，B 被过滤
- And 检索日志中记录了本次的过滤表达式，且断言环节无失败

#### M1.4 负向评测集（强制）

**FR-M1-004** 系统应提供**越权评测集**，作为上线验收的强制项：
- 构造 ≥ 30 条「用户无权但库中存在答案」的问题
- 每条在文档中注入 128 位随机哨兵令牌（sentinel token）
- 校验范围：提示词、答案正文、引用列表、原始 JSON 响应体
- **通过标准：哨兵令牌泄露率 = 0.00%**
- 反事实不变性校验：即使受限文档从库中物理删除，无权用户的响应也必须完全一致（即不得因文档存在与否泄露信息）

**验收**
- Given 30 条越权问题 + 30 条有权问题
- When 执行评测
- Then 越权问题全部不命中受限内容，哨兵泄露率 0.00%
- And 有权问题仍能正常召回（**不得为过安全测试而牺牲正常功能**）

#### M1.5 审计日志

**FR-M1-005** 每次检索应记录：主体（用户/Key/Agent）、时间、授权库 UUID 列表、ACL 过滤表达式、召回片段 id、断言失败的片段数、被丢弃片段数。

**FR-M1-006** 系统应对过滤失效事件（断言失败次数 > 0，或检测到无权片段进入上下文）产生告警日志（warn 级，含 traceId）。

#### M1.6 管理端配置

**FR-M1-007** 管理后台知识库详情应新增「访问控制」配置区：
- 库级默认值：默认可见组、默认密级（作用于新上传文档）
- 文档级覆盖：单个文档可覆盖库级默认
- 存量规范化：展示「待规范化」文档数并提供一键回填入口

**BR-7**：⚠️ **任何可编辑的 KB 配置字段都必须在 `KbInfoResp` 中能读回来**。这是本项目已踩过的坑（`KbInfoResp` 缺检索开关字段，导致弹窗显示为关闭，保存一次就把库里配置关掉）。新增字段必须同步在 `KbInfoResp` 中暴露。

#### M1.7 存量迁移兼容

**FR-M1-008** 迁移后存量行为必须**保持不变**：在管理员未配置任何 ACL 之前，私有库仅 owner 及其被授权方可见、公开库所有人可见，与改造前完全一致。

### 模块 M2：知识检索开放 API · P0

#### M2.1 端点定义

**FR-M2-001** 系统应新增端点 `POST /ext/v1/knowledge/retrieve`，语义为**只检索不生成**。

**请求体**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `query` | string | 是 | 查询串，1–2000 字 |
| `kbUuids` | string[] | 否 | 指定知识库列表；**不传则取该 Key 授权的全部库** |
| `topK` | int | 否 | 返回条数，默认 5，上限 20 |
| `minScore` | number | 否 | 最低相似度，默认 0（走库配置）。⚠️ 量纲为 `(1+cos)/2`，默认 0.6 等价于 cos ≥ 0.2 |
| `withNeighbor` | boolean | 否 | 是否返回左右扩窗片段，默认沿用库配置 |
| `responseMode` | string | 否 | `blocking`（默认）/ `streaming` |

**响应体**

```json
{
  "query": "差旅报销标准",
  "skippedKbUuids": [{"uuid": "xxx", "reason": "NO_PERMISSION"}],
  "contents": [
    {
      "text": "……【差旅管理办法·第3段】",
      "score": 0.78,
      "kbUuid": "kb-1",
      "docUuid": "doc-1",
      "docTitle": "差旅管理办法.pdf",
      "position": 3,
      "isNeighbor": false
    }
  ],
  "usage": { "embeddingTokens": 0 },
  "traceId": "..."
}
```

**业务规则**
- BR-8：**多库联合**：`kbUuids` 支持多个库，返回结果**按 score 全局降序**合并，**不按库分组**。
- BR-9：**无权限的库静默跳过**，但必须在 `skippedKbUuids` 中列明原因（`NO_PERMISSION` / `NOT_FOUND` / `DISABLED`）。⚠️ **不得通过"过滤后为空"的响应差异泄露库是否存在**——`NOT_FOUND` 与 `NO_PERMISSION` 对无权调用方返回**一致的响应**。
- BR-10：**引用可溯源**：每个 `contents` 项必须携带 `docUuid` + `position`，使调用方能点回原文。⚠️ 出处抬头只修改返回文本，**不得修改 embedding 输入**（本项目既定铁律）。
- BR-11：**不调用 LLM**，因此不产生 LLM token 消耗；`usage` 只含 embedding 侧。
- BR-12：ACL 过滤**必须生效**，复用 M1 的过滤表达式与双保险断言。

**Given/When/Then 验收**
- Given Key 绑定了库 A、B，用户对 A 有权限、对 B 无权限
- When 调用 retrieve，指定 `kbUuids=[A,B]`
- Then 返回内容全部来自 A，`skippedKbUuids` 含 B 且 `reason=NO_PERMISSION`
- And 响应中不含任何 LLM 生成文本
- And 每次调用在检索日志中有对应记录

#### M2.2 Key 与多库的关系

**FR-M2-002** 系统应支持创建**平台级** API Key（不绑单库，授权一组库），以支持多库联合检索需求。现有 `ExtApiService` 的 Key 与资源一对一模型需扩展为「Key ↔ 多资源」。

**BR-13**：向后兼容——现有绑单库的 Key 行为不变。

#### M2.3 限流与配额

**FR-M2-003** 开放 API 必须有：
- 单 Key QPS 限流（默认 20 QPS，可配置）
- 单 Key 日调用量上限（默认 10000 次/日，可配置）
- 超限返回 429 + `Retry-After`

**BR-14**：⚠️ 本项目历史教训——「验证码图片接口无频控」「残留撑爆配额」。新增接口必须**先有配额再上线**。

### 模块 M3：KB → MCP Server · P0

#### M3.1 服务注册

**FR-M3-001** 系统应支持将任一知识库注册为 MCP Server，端点形式：

```
POST /mcp/kb/{kbUuid}      (Streamable HTTP)
```

**BR-15**：MCP 端点复用现有 `/mcp` 模块的鉴权机制（ExtApi Key，`resourceType=knowledge`）。⚠️ 注意：现有 `ExtApiAuthFilter` 已修过 context-path 拼接 bug，新增路径须走同一套归一化逻辑。

#### M3.2 暴露的工具

**FR-M3-002** 每个 KB MCP Server 暴露以下工具：

| 工具名 | 入参 | 出参 |
|---|---|---|
| `kb_search` | `query`(必填), `topK`(可选), `minScore`(可选) | 片段数组（含 text / score / docUuid / docTitle / position） |
| `kb_get_document` | `docUuid`(必填), `position`(可选) | 文档标题 + 指定段原文 / 全文 |

**业务规则**
- BR-16：`kb_search` 的召回逻辑**必须与 M2 完全一致**（同一内核、同一 ACL、同一扩窗/rerank 配置）。⚠️ **禁止为 MCP 另写一套检索实现**，否则必然出现两套行为不一致。
- BR-17：`kb_get_document` 返回原文前**必须再次校验 ACL**——检索时的权限可能在两次调用之间被撤销。
- BR-18：MCP 侧返回的文本**必须带出处抬头** `【文档名·第N段】`。

#### M3.3 资源暴露

**FR-M3-003** 系统应将知识库作为 MCP **resource** 暴露（`kb://{kbUuid}/{docUuid}` 形式），支持 MCP 客户端直接读取完整文档。

**BR-19**：resource 读取同样受 ACL 约束，无权时返回权限错误，**不得返回空文档或文档存在性提示**。

#### M3.4 多库聚合 MCP

**FR-M3-004** 系统应支持创建一个「聚合 MCP Server」，将多个知识库挂载为一个 MCP 服务，供需要跨库检索的客户端（如 Coding Agent）使用。

#### M3.5 接入文档

**FR-M3-005** 系统应在管理端生成标准接入文档，内容包含：端点地址、鉴权方式、工具清单、入参出参 schema、示例请求/响应、常见错误码。**示例中的所有 ID 均为虚构**，不得使用真实业务数据。

**验收（真实浏览器测试，非仅 API）**
- Given 用户在 Cursor/Cherry Studio 等任一 MCP 客户端配置 `kb-{uuid}`
- When 用户提问「<某个只有该库能回答的问题>」
- Then 客户端成功调用 `kb_search` 并返回带出处的答案
- And 用户能从答案点回原文
- **本项必须做真实客户端连接测试并截图留证，不能仅验证接口返回 200**

### 模块 M5：知识包导出与分享 · P1

**FR-M5-001** 系统应支持将「知识库 + 检索参数 + 提示词 + 可选 Skill 脚本」打包为一个**知识包**并导出为 ZIP。

**包结构**

```
knowledge-pack/
├── pack.json          # 元信息：名称、版本、kbUuid、检索参数、导出时间
├── SKILL.md           # 标准 frontmatter(name/description) + 使用说明 + 检索策略
├── config.json        # topK / minScore / withNeighbor / rerank 等
└── resources/         # 可选：辅助脚本与模板
```

**FR-M5-002** 知识包应可被导入还原：导入时校验 `pack.json` 格式，kbUuid 不存在时明确报错而非静默创建空库。

**BR-24**：⚠️ 本项目已有踩坑——**手工创建的技能磁盘上什么都没有**（只有 DB 的 name/desc/content），导出必须用 `buildSkillMd(skill)` 兜底生成**虚拟 SKILL.md**（打 `virtual=true` 标记），才能保证「导出 → 再导入」还原同一资产。知识包沿用此约定。

**FR-M5-003** 知识包应支持设置分享范围：私有 / 组织内公开 / 持 Key 可用。
- 组织内公开时，导入方**仍然只能获得其自身权限内的片段**（分享的是「检索能力」不是「数据」）
- ⚠️ 这是关键设计：**共享知识包不等于共享数据**

**验收**
- Given 管理员 A 创建含库 X 的知识包并导出
- When 管理员 B 导入该包
- Then B 能使用该包发起检索
- And 若 B 无 X 的权限，检索返回空并提示无权限，**不报错也不泄露 X 存在**
- And A 导出 → B 导入 → B 再导出，三个包 `pack.json` 内容一致（往返一致）

### 模块 M6：用户维度长期记忆 · P1

**FR-M6-001** 系统应支持绑定 `userId`（而非仅 `characterId`）的长期记忆，使记忆在该用户的**所有 Agent、所有会话**间共享。

**业务规则**
- BR-25：记忆提取后**必须经用户确认**才写入。⚠️ 未经确认直接写入会导致记忆被模型幻觉污染（这是 WeKnora 等产品的一致做法）。
- BR-26：记忆类型分为**用户画像**（你是谁：角色、偏好）/ **业务事实**（做过什么：处理过哪些工单、用过什么口径）/ **技能经验**（这事过去怎么做的），对应阿里云 Memory Studio 的三分法。
- BR-27：记忆召回**不覆盖**知识库检索，二者并行，来源在答案中可区分标注。
- BR-28：用户应能查看、编辑、删除自己的全部记忆（**记忆归属权归用户，不归 Agent**）。

**FR-M6-002** 管理端与用户端应提供记忆管理入口：列表、按类型筛选、批量删除。

**FR-M6-003** 系统应提供记忆开关（用户级关闭长期记忆），关闭后不再提取也不再召回。

**验收**
- Given 用户 A 在 Agent X 中确认了一条记忆
- When 用户 A 在 Agent Y（新会话）中提问相关问题
- Then 记忆被召回并用于回答，答案中标注「记忆来源」
- And 用户 A 在记忆管理页可看到、编辑、删除该记忆
- And 关闭记忆开关后，不再提取也不再召回

## 八、业务流程与状态流转

### 8.1 M1 ACL 生效流程

```
文档上传 → 分块（sentence_cn/512/overlap=0）→ 写入 ACL 元数据（不清洗、不参与向量化）
   ↓
检索请求到达 → 解析主体（用户 / API Key / Agent 发起者）→ 计算可见组
   ↓
构造 where：And(IsIn(kb_uuid, 授权库), Or(sensitivity=PUBLIC, IsIn(visibility_groups, 可见组)))
   ↓
向量库检索（第一道）
   ↓
应用层断言（第二道）→ 失败片段丢弃 + 写审计 + warn 告警
   ↓
扩窗（rerank 之后、出处抬头之前）→ 加出处抬头 → 进上下文
```

### 8.2 迁移与存量状态机

ACL 规范化状态：`PENDING`（待回填）→ `NORMALIZED`（已回填）。存量数据初始为 `PENDING`，按 BR-8 推导规则保证行为不变。

### 8.3 M3 MCP 连接状态机

`CREATED`（已生成端点）→ `ACTIVE`（可连接）→ `SUSPENDED`（管理员暂停）→ `DELETED`

- 库被删除时，MCP 端点同步置为 `DELETED`，返回 404
- 库 ACL 变更**不影响** MCP 连接状态，但**立即影响**检索结果

## 十、权限与安全要求

| 编号 | 要求 |
|---|---|
| SEC-01 | ACL 过滤**必须**在向量检索阶段执行，**严禁**以 prompt 约束、**严禁**取回后再筛 |
| SEC-02 | ACL 过滤条件**必须**来自请求主体，**严禁**来自 query 内容或请求体参数 |
| SEC-03 | 双保险：向量库过滤 + 应用层断言，两道都过才进上下文 |
| SEC-04 | 无权资源的存在性**不得**通过响应差异泄露（`NOT_FOUND` 与 `NO_PERMISSION` 返回一致） |
| SEC-05 | 开放 API 必须鉴权 + 限流 + 配额 + 审计四件套齐备 |
| SEC-06 | `query_text` 与日志落库前脱敏 PII |
| SEC-07 | 日志表保留期 ≤ 90 天，到期自动清理 |
| SEC-08 | 记忆归属权归用户；Agent **不得**读写他人记忆 |
| SEC-09 | 知识包共享的是「检索能力」而非「数据」，导入方始终受自身 ACL 约束 |

## 十一、异常处理清单

| 编号 | 场景 | 处理 |
|---|---|---|
| EX-01 | 请求的 kbUuid 不存在 | 返回 404 + `NOT_FOUND`（对无权调用方与不存在返回一致） |
| EX-02 | 部分库无权限 | 跳过并列入 `skippedKbUuids`，**不中断整体请求** |
| EX-03 | 全部库无权限 | 返回空 `contents` + `skippedKbUuids`，**不报错** |
| EX-04 | `query` 为空或超长 | 400 + `A0002 参数校验不通过` |
| EX-05 | `topK` 超上限 | 截断到 20，不报错 |
| EX-06 | 限流超限 | 429 + `Retry-After` |
| EX-07 | 配额耗尽 | 429 + 明确文案「今日调用已达上限」 |
| EX-08 | API Key 失效/撤销 | 401 |
| EX-09 | 库被删除但 MCP 端点仍存在 | 404 |
| EX-10 | 检索超时 | 504 + traceId |
| EX-11 | LLM 不可用（仅问答场景） | 明确错误，**不返回空答案伪装成功** |
| EX-12 | ACL 断言失败 | 丢弃片段 + 写审计 + warn 告警，**继续处理其余片段** |
| EX-13 | 向量库不可用 | 降级为关键词检索（若已配置）；否则明确报错 |
| EX-14 | 知识包导入时 kbUuid 不存在 | 明确报错，**不静默创建空库** |
| EX-15 | 日志写入失败 | **吞掉并计数告警，不影响主链路** |
| EX-16 | 记忆提取的 LLM 调用失败 | 跳过本次提取，不影响对话 |

### 14.2 关键实现铁律（开发必读，源自本项目历史踩坑）

| # | 铁律 |
|---|---|
| 1 | **出处抬头只改返回文本，不得改 embedding 输入**，否则需重建全量索引 |
| 2 | **ACL 元数据不参与向量化**，修改 ACL 不需重建索引 |
| 3 | **M2 与 M3 必须复用同一检索内核**，禁止另写实现 |
| 4 | 前端加节点/字段是**「六处注册」**不是五处（漏第六处 = 数据入库但界面不显示） |
| 5 | vue-i18n 文案禁字面花括号，用 `braceLiteral`，新增文案须做守卫负向验证 |
| 6 | MyBatis jsonb 字段必须用 `resultMap` + `updateById`，否则静默为 null |
| 7 | **任何可编辑的 KB 配置字段必须在 `KbInfoResp` 能读回来**，否则弹窗显示为关闭、保存一次即关掉配置 |
| 8 | 迁移脚本须幂等，且同步 `all_ddl.sql` / `all_dml_cn.sql` / `all_dml_en.sql` |
| 9 | 测试断言必须真实：**空值恒真 / 连接失败误判 OK / 僵尸 SQL** 是七类假 OK 的主要来源 |
| 10 | 界面功能必须**真实浏览器点击测试**，不能仅验证 API 返回 200 |
