# T6-04 overlap 三组对照评测 · 真实跑分结论

> 跑分日期：2026-10-21　| 语料：`docs/cn`（37 篇产品文档，与 `kb-eval/golden.jsonl` 同源）
> 铁律 9：以下全部数字来自真实检索/切分链路，无任何占位或推算值。

## 一、结论（先看这个）

**保持默认 `overlap = 0` 不变。** 理由有两条实测证据：

1. **切分层**：overlap 确实生效，但只在「单个句子本身就超过段大小」时才触发。全语料 37 篇里，
   106 个段中只有约 4~5 段真的发生了重叠，重复字符占比 0.33%~1.6%。
2. **检索层**：三组（overlap 0 / 51 / 102）在同一题库上的**全部指标逐位相同**——说明这 0.3%~1.6% 的
   重复没有换来任何召回改善，反而会让索引变大、重复内容稀释候选池。

任务书要求「拿到可复现的量化结论前默认值保持不变」——本报告即该结论，值仍为 0。

### 3.3 读数说明

- 段数几乎不变（106 → 106/107）：overlap **不是**「每段都重复上一段尾巴」，
  它只在**单个句子超过段大小**、需要跨段拼装时才启用（langchain4j 的 overlap 语义：
  追加上一块的最后一个子段；`CjkSentenceSplitter` 的打包单位是句子）。
- 字符增量 = 触发重叠的段数 × overlap 量级：102 token × 约 5 段 ≈ 500 token，
  与实测增量（43623 − 43165 = 458）吻合。
- 中文产品文档的句子普遍短于 512 token，所以 overlap 在真实语料上**几乎不被触发**。

## 四、为什么默认 0 是对的（机制层面）

| 维度 | overlap=0 | overlap>0 |
|---|---|---|
| 召回质量 | 基线 | 本次实测**无差异**（三组逐位相同） |
| 索引体积 | 基线 | +0.3%~1.6% 字符，重复内容挤占候选池 |
| 段边界语义 | 落在句子边界（sentence_cn），语义完整 | 句子本身够短时**不触发**，无收益 |
| 风险 | 跨段截断风险极低（句子粒度） | 触发时是「整句重复」，收益有限、成本确定 |

这也印证了迁移 024 的原始判断（生产代码注释里写的那句）：*「小 overlap 没效果，大 overlap 等于整块复制」*——
本次用真实语料把它量化了。

## 六、遗留

- 「邻近扩窗」（`WINDOWS=1,2`）是另一个正交维度（检索期扩窗，非分块期 overlap），
  已在前几批单独验证过（结论：中文分句 + 左右扩窗有效），本报告不重复展开。
- 客户真实知识库（非产品文档）语料分布不同，overlap 的触发率可能更高；
  若要对外承诺「overlap 无用」，建议在 1~2 个真实客户库上各跑一次同样的三组对照。
